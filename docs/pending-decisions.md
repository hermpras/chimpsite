## 2. Data Model & Database (Stage 1 - Resolution Status)

| ID          | Topic                                        | Status                    | Decision Outcome & Reference                                                                                                                                                                                                                                                                                                        |

| **DEC-005** | **Primary Account Identifier**               | `RESOLVED (Oct 13, 2026)` | `User` is the root record with an independent ID (`cuid`), possessing a 1:1 relation to `WalletIdentity` (primary identity) and a 1:1 relation to `XIdentity` (linked social account).                                                                                                                                              |
| **DEC-006** | **Multi-Chain Management**                   | `RESOLVED (Oct 13, 2026)` | No blockchain minting, smart contracts, or on-chain transfers. All allocations are recorded in PostgreSQL. The `chainId` column is retained as an EVM network reference (default 1 / Ethereum).                                                                                                                                     |
| **DEC-007** | **Whitelist Allocation Verification Method** | `RESOLVED (Oct 13, 2026)` | Allocations are verified and tracked purely off-chain through PostgreSQL using separate lifecycle stages: `WLQualification` (qualification), `WLQueueEntry` (queue), `WLSlot` (slot allocation), and `WLStatusHistory`.                                                                                                             |
| **DEC-008** | **Claim Execution Mechanism (Gas Fees)**     | `RESOLVED (Oct 13, 2026)` | No on-chain transactions; drop claims are conducted entirely off-chain without user gas fees or third-party relayers.                                                                                                                                                                                                               |
| **DEC-009** | **Gift Engine & Trait Ownership**            | `RESOLVED (Oct 16, 2026, Updated Oct 29, 2026)` | Each trait copy is a distinct `InventoryItem` entity with a unique edition. Gifting transfers an existing extra item rather than minting new copies. **Category Retention Rule:** Eligibility is calculated by trait category (`BG`, `FUR`, `CLOTHING`, `HEADWEAR`, `EYEWEAR`); sender must own >= 2 items in that category and retain >= 1 item in the category after gifting. 1 gift per wallet per UTC day; recipient must not already own exact trait; recipient cannot be self, banned, or have allocated WL slot. Recipient lookup via X username or wallet address implemented in `GET /api/gifts/recipient` with fail-safe JSON response handling. **Cron Elimination & Event-Driven Expiry:** Background cron sweeps were eliminated due to budget constraints (approved decision). The 24-hour expiry is enforced event-driven via lazy on-demand evaluation upon `acceptGift()` (rejecting expired gifts with 410 `GIFT_EXPIRED` and atomically unlocking trait to sender) and opportunistic cleanup on `GET /api/gifts` (`expireUserGiftsOpportunistically`). Senders may also cancel pending gifts manually anytime. Evidence: `server/inventory/gift.ts`, `app/api/gifts/route.ts`, `app/api/gifts/recipient/route.ts`, `components/inventory/GiftModal.tsx`, `components/inventory/TraitGrid.tsx`. |
| **DEC-010** | **Admin Role Authorization**                 | `RESOLVED (Oct 13, 2026)` | Admin authorization is defined through the `UserRole` enum (`USER`, `MODERATOR`, `ADMIN`, `SUPER_ADMIN`) and the `AdminRole` model with granular permission lists (`permissions: String[]`).                                                                                                                                        |
| **DEC-011** | **Audit Trail & Logging**                    | `RESOLVED (Oct 13, 2026, Updated Oct 30, 2026)` | Sensitive mutations, review actions, slot allocations, and bans are recorded in the PostgreSQL `AuditLog` table capturing the actor (`actorId`), action type, entity payload, and audit metadata. **Audit Log Dashboard & Query API (DONE):** Dedicated read-only endpoint `GET /api/admin/audit-logs` strictly restricted to `SUPER_ADMIN` (rejecting `ADMIN` and `MODERATOR` with 403, and unauthenticated requests with 401). Includes filtering (`action`, `entityType`, `actorId`, `from`, `to`), safe pagination (clamped to max 100), stable ordering (`createdAt DESC, id DESC`), and safe projection omitting confidential `actorIp` and `userAgent`. Admin UI integrated in Admin Dashboard (`components/admin/AdminAuditLog.tsx`, `components/admin/AdminSidebar.tsx`) with detail inspection modal for `oldValues`, `newValues`, and `metadata`. Verified with 98 test files, 1,232 passing tests, clean typecheck, 0 lint errors (17 pre-existing warnings), and successful build (commit `dd4156881d3bd17d25dc2876c87850eb12c54591`). |

## 3. Advanced Policies & Business Rules

| ID          | Topic                                                          | Status                    | Decision Outcome & Reference                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            | Impact                                                                                                                       |
| ----------- | -------------------------------------------------------------- | ------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| **DEC-012** | **Ban Policy Matrix & Abuse Flag Thresholds**                  | `RESOLVED (Oct 28, 2026)` | **1. Sybil Cluster IP Threshold:** Threshold set at ≥ 5 distinct wallets per IP per single drop cycle. Creates an `AbuseFlag` for manual investigation; strictly no automated banning based on IP alone (`server/drops/claim.ts`).<br>**2. Moderator Role & Permissions (Option B):** Implemented without schema migration using `AdminRoleType.MODERATOR` with permissions restricted to `REVIEW_EVIDENCE` and `REVIEW_FLAGS`. Compatible with existing `AdminRole` model and authorization logic (`server/auth/session.ts`, `components/admin/AdminSidebar.tsx`).<br>**3. Permanent Ban Revocation:** Permanent bans can only be revoked by `SUPER_ADMIN`. Regular `ADMIN` attempts are strictly rejected with HTTP 403 `INSUFFICIENT_PRIVILEGE`. Temporary/feature-scoped bans remain revokable by `ADMIN` (`server/admin/ban.ts`).<br>**4. Dual-Layer Rate Limiting & Admin Management:** Dual-layer wallet (5 req/120s) and IP (10 req/60s) rate limits on claims (`app/api/drops/claim/route.ts`). Admin Abuse Flags API (`app/api/admin/abuse-flags/**`) and Dashboard UI (`components/admin/AdminAbuseFlags.tsx`) with full AuditLog tracking. | Hardened `revokeBan()` authorization, automated abuse flag detection on drop claims, dual-layer IP rate limiting, moderator role permission scoping (`REVIEW_FLAGS`), Admin Abuse Flags API & UI, and complete integration test suite (`tests/integration/dec012-integration.test.ts`). |
| **DEC-013** | **Whitelist Queue Priority Score & Reconciliation Parameters** | `RESOLVED (Oct 16, 2026)` | **First-qualified-first-allocated with timestamp ordering and stable sequence tie-breaker.** Queue ordering strictly uses the timestamp when all qualification requirements were first satisfied (`joinedAt`), with `queueNumber` as stable tie-breaker. Priority score formula omitted per approved decision. Evidence: `server/whitelist/qualification.ts`.                                                                                                                                                                                                                    | Slot allocation priority determination for the Whitelist queue service worker.                                              |
| **DEC-021** | **WL Initial Capacity & Canonical Program Configuration**      | `RESOLVED (Nov 1, 2026)`  | **Canonical Whitelist Capacity is strictly 1,000 slots (corrected from 2,000 slots).** The canonical `WLProgram` configuration will use `totalSlots = 1000`. Record creation, SQL writes, and database seeds remain deferred while two backend safeguards are being completed: (1) Shared Pessimistic Capacity Guard (`SELECT ... FOR UPDATE` on `WLProgram`), and (2) Conditional Atomic Revocation with Lower-Bound Protection & Revoked Slot Record Reuse. All documentation and reports strictly reflect initial capacity of 1,000 slots. | Establishes canonical capacity for `WLProgram` entity configuration and guarantees capacity invariants ($0 \le \text{allocatedSlotsCount} \le 1000$). |
| **DEC-022** | **GTD Revocation Full Whitelist Disqualification Policy** | `RESOLVED (Nov 1, 2026)` | **Full Whitelist Program Disqualification on GTD Revocation.** When a user's GTD slot is revoked (`REVOKED_MANUAL_ADMIN` or `REVOKED_SYSTEM`), the revocation constitutes a full program disqualification. The revoked user is immediately ineligible for the entire Whitelist program, including Guaranteed (GTD) slot allocation and OpenSea FCFS Allowlist. `WLQueueEntry` records are strictly retained for audit trail and sequential tie-breaker integrity, but revoked participants are permanently excluded from OpenSea FCFS CSV exports and counted under `bannedOrDisqualifiedCount` in pre-export audit summaries. `GET /api/whitelist/status` strictly prioritizes `phase: "REVOKED"` over `phase: "FCFS_REGISTERED"` for any user with a revoked slot or qualification history who does not hold an active GTD slot. Auto-restoration and auto-promotion are strictly prohibited; qualification evaluation (`evaluateUserQualification`) returns `phase: "REVOKED"` with `qualified: false`. Restoration may only be performed by an authorized administrator through an explicit action recorded in `AuditLog`. Evidence: `server/whitelist/revoke.ts`, `server/whitelist/qualification.ts`, `server/admin/opensea-export.ts`, `app/api/whitelist/status/route.ts`. | Disqualifies revoked GTD holders from OpenSea FCFS export, enforces `REVOKED` priority over `FCFS_REGISTERED` in user status API, blocks qualification auto-restoration, and mandates immutable audit logging for any administrative restoration. |
